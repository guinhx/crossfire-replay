# Format overview

This project supports replay data commonly found with `.cfr`, `.cfo`, and `.cfn` extensions. The layouts are inferred from observed files and reference-code research; they are not official specifications.

## Data model

```text
.cfr  -> SimpleProtocol payload, optionally prefixed by a 32-byte checksum block
.cfo  -> Brotli wrapper -> SimpleProtocol or PacketSimulator payload
.cfn  -> AES-CBC and Brotli wrapper -> SimpleProtocol or PacketSimulator payload
```

| Extension | Expected outer representation | Common observed payload | Document class |
|---|---|---|---|
| `.cfr` | None | SimpleProtocol | `CfrDocument` |
| `.cfo` | Brotli wrapper | PacketSimulator | `PacketSimulatorReplayDocument` |
| `.cfn` | Encrypted Brotli wrapper | PacketSimulator | `PacketSimulatorReplayDocument` |

The library detects payload bytes after unwrapping rather than binding a payload type to an extension. Its writers can place either built-in document type in `.cfo` or `.cfn` wrappers.

An observed Windows replay directory is:

```text
%USERPROFILE%\Documents\Cross Fire\Replay\
```

## SimpleProtocol

SimpleProtocol is the project's classification for the `cfrversion` stream used by CFR documents. It contains sequential match messages such as map information, round transitions, scores, and player events.

Each message begins with a `SimpleProtocolId`; most supported layouts then contain a protocol version, timestamp, and message-specific body.

See [CFR SimpleProtocol](cfr-simple-protocol.md).

## PacketSimulator and ILT

PacketSimulator is the project's classification for inner payloads containing timestamped LithTech/ILT packet data. Observed payloads include spectating, game, and special-effect archives, plus metadata and other intermediate data whose structure varies by layout.

The enum names `LegacyV2022` and `ModernV2026` distinguish two layouts recognized by this repository. They refer to reference fixtures and signatures, not official names or authoritative release dates.

See [CFN PacketSimulator](cfn-packet-simulator.md).

## Evidence and validation

Format behavior is supported by one or more of the following:

- synthetic tests for a specific byte layout or codec;
- writer/reader tests that assert selected fields or bytes;
- byte-preserving reconstruction tests against optional local fixtures.

Round-trip equality is strong evidence that a writer preserves the represented bytes. It does not, by itself, prove that field names or decoded semantics are correct. Likewise, wrappers generated by the project can be decoded by the project, but game-client acceptance has not been established by these tests.

## Known limitations

- Not every ILT `EMessageId` has a semantic decoder. Valid unsupported IDs may become `LtUnknownDecoded`.
- Some client-to-server packets, including observed `VelAndRot` and short `SetWeaponSlot` variants, remain under investigation.
- `ReadCompPos` uses default world bounds when map-specific minimum and maximum bounds are unavailable.
- Layout detection recognizes only the signatures currently implemented; unfamiliar payloads may be returned as `PacketSimulatorInnerFormat.Unknown`.

Report unsupported data with the **Decode / format gap** issue template.
